# SYLVA 贡献者指南与角色说明

> **本文件**：描述 TOE-SYLVA 项目的贡献者角色分工、协作流程与质量规范。
> **适用对象**：所有参与 SYLVA 项目的贡献者——人类研究者、AI 辅助 Agent、自动化 CI 流水线。
> **最后更新**：2026-08-18

---

## 一、项目角色体系

TOE-SYLVA 采用"人类决策 + AI 执行 + 机器验证"的三层协作模型。以下角色按职责划分：

### 1.1 项目负责人（PI / Admin）

- **职责**：研究方向决策、版本发布审批、理论声明治理级别最终裁定
- **权限**：git push / force-push / merge、版本号分配、CLAIM→THEOREM 升级审批
- **对应文件**：`framework/proof_status.md`（声明分层治理）、`framework/BLIND_PREDICTIONS.md`（盲登记冻结）

### 1.2 群管理员（Main Agent / Scheduler）

- **职责**：复杂任务拆解与派发、跨 Agent 协调、进度追踪与验收
- **工作流**：
  1. 接收 USER 的研究/开发请求
  2. 将复杂任务拆解为可并行执行的子任务
  3. 按优先级分配给各专业 Agent
  4. 汇总各 Agent 的交付结果，进行交叉验证
  5. 向 USER 汇报最终结果
- **关键能力**：任务分解、优先级评估、资源调度

### 1.3 搜索规划师（Search Planner）

- **职责**：深度拆解用户的信息收集需求，制定多维度搜索策略
- **工作流**：
  1. 分析信息需求的核心维度
  2. 构建多组高级搜索词（广度 + 深度）
  3. 规划搜索源优先级（学术数据库 > 预印本 > 百科 > 社交平台）
  4. 将搜索子任务汇报给群管理员
- **产出格式**：搜索策略文档（含关键词矩阵、信息源列表、优先级排序）

### 1.4 并行搜索员（Parallel Searcher A/B/C）

- **职责**：高效执行群管理员分配的具体搜索任务，全方位深度挖掘网络资料
- **工作流**：
  1. 任务解析：提炼核心关键词，构建多组高级搜索词
  2. 深度挖掘：web-search 初筛 → web-reader 深入长文本提取
  3. 工具破壁：对知乎/小红书等防爬平台果断调用 agent-browser 模拟浏览器抓取
  4. 信息提纯：过滤 SEO 农场与营销软文，交叉比对多来源
- **验收标准**：
  - 交付内容包含具体数据、真实案例、专业见解
  - 对重要数据标明出处
  - 遇到复杂网页时成功触发 agent-browser

### 1.5 报告汇总员（Report Synthesizer）

- **职责**：对搜索员收集的信息进行深度交叉验证与梳理，生成高质量研究报告
- **工作流**：
  1. 汇集各搜索员的交付材料
  2. 交叉验证关键数据与争议性观点
  3. 逻辑梳理与结构化组织
  4. 生成排版精美、图文并茂的研究报告
- **产出格式**：结构化研究报告（Markdown + 图表 + 引用链）

## 二、AI 辅助写作规范

SYLVA 项目部分论文和代码是在 AI 辅助下生成的。为防止 AI 幻觉污染学术内容，所有贡献者必须遵守以下规则（详见 `CONTRIBUTING.md`）：

### 2.1 强制规则

1. **禁止未经验证的声明**：AI 生成的事实声明（数学公式、引用文献、实验数据、人名、定理名）必须追溯到可验证原始来源（arXiv、DOI、权威教科书页码）。
2. **引用完整性**：每个 `[N]` 引用必须对应真实存在的出版物，在 `REFERENCES_VERIFIED.bib` 中有条目，通过 web-search 验证标题、作者、年份正确。
3. **显式标记**：AI 生成章节必须在开头添加 `> ⚠️ AI-ASSISTED` 标记。
4. **幻数禁止**：不得出现"巧合"匹配的常数（如 α⁻¹ = 137.036 与 n_CS = 137 的"精确对应"），除非有严格数学证明。
5. **遵循协议**：所有涉及 AI 辅助写作的贡献者必须先阅读 `papers/AI_FAILURE_TO_VERIFIABLE_PROTOCOL.md`。

### 2.2 常见 AI 幻觉类型

| 类型 | 描述 | 检查方法 |
|------|------|----------|
| 引用虚构 | 编造不存在的论文 | Web-search 验证标题+作者 |
| 定理虚构 | 声称某人证明了不存在的定理 | 查 MathSciNet / arXiv |
| 数值幻觉 | 计算数值恰好等于某已知常数 | 独立验证数值计算 |
| 概念拼接 | 将两个真实概念缝合为不存在的"新概念" | 搜索合并后的概念名 |
| 过度泛化 | 将特定领域结论推广到不适用领域 | 检查前提条件 |
| 时间错误 | 声称某结果在某年被证明（实际是后来） | 查原始论文发表年份 |

## 三、验证清单

提交新论文/新模块前，必须逐项检查：

- [ ] **引用验证**：所有引用文献已通过 web-search 验证存在且内容匹配
- [ ] **人物时间线**：所有提及的数学家/物理学家的归属已验证
- [ ] **数学公式**：所有公式已独立推导或交叉验证，无"巧合"匹配
- [ ] **数值声明**：所有数值结果有对应 `verify_*.py` 脚本且全部通过
- [ ] **交叉引用**：与框架内其他文档的交叉引用不为空占位符
- [ ] **AI 标记**：AI 辅助生成的段落已显式标记
- [ ] **幻觉检查**：已针对失败模式分类逐项排查
- [ ] **Lean 形式化**：核心模块零 `sorry`（或 `axiom` 有完整 docstring）
- [ ] **参考文献格式**：符合 BibTeX 规范，包含 arXiv ID 或 DOI
- [ ] **README 更新**：如新增论文，已更新 README.md 的 Paper Index

## 四、验证脚本规范

每个论文目录的 `verify_*.py` 必须：

1. 包含 `run_all_tests()` 函数
2. 对核心公式进行数值验证（非仅恒等式）
3. 退出码 0 表示全部通过
4. 失败时打印具体失败项和期望值/实际值

**命名约定**：
- `verify_<主题>.py` — 标准验证脚本
- `validation_<主题>.py` — 综合验证套件
- `check_<主题>.py` — 检查脚本

**执行约定**：
```bash
python3 verify_<topic>.py && echo "PASS" || echo "FAIL"
```

## 五、理论声明治理

SYLVA 框架建立四级声明标签，避免 "conjecture / claim / theorem" 混用（详见 `framework/proof_status.md` v1.1）：

| 标签 | 含义 | 数学标准 |
|------|------|----------|
| **THEOREM** | 形式化证明已通过 Lean/Agda 交叉验证，核心部分无 `postulate` | 证明已由同行评议或可机器验证 |
| **THEOREM\*** | 数学主体已证明，但依赖未在当前框架内验证的已知定理 | 引用完整性已确认 |
| **CLAIM** | 有推理支撑、数值吻合或引用佐证，但未经独立形式化/评议 | 推导已记录但未穷尽 |
| **CONJECTURE** | 推测性论断，逻辑连贯但缺乏严格验证 | 可证伪、可测试 |

## 八、贡献流程

### 8.1 新增论文/综述

1. 在 `papers/` 下创建 `<主题>_综述/` 目录
2. 创建 `README.md`（目录说明、文件清单、交叉引用）
3. 创建 `<主题>_综述.md`（200–600 行综述正文）
4. 创建 `verify_<主题>.py`（数值验证脚本，exit 0）
5. 更新 `papers/README.md` Paper Index
6. 通过验证清单全部检查项

### 8.2 新增 CNF 桥接文档

1. 在 `framework/` 下创建 `<编号>_<领域>_cnf.md`
2. 包含：CNF 框架映射、领域应用、S 预测（带证伪条件）
3. 更新 `framework/INDEX.md` 与 `framework/DASHBOARD.md`
4. 在 `framework/BLIND_PREDICTIONS.md` 登记 S 预测

### 8.3 新增 Lean 形式化

1. 在 `sylva_formalization/SylvaFormalization/` 下创建 `SYLVA_<Module>.lean`
2. 在 `All.lean` 注册 import
3. 在 `lakefile.lean` 注册 root
4. 确保 `lake build` 通过
5. 核心 theorem 零 sorry；如使用 axiom，须有完整 docstring

## 九、协作礼仪

- **任务接收**：收到群管理员 @ 后立即确认，明确任务边界与验收标准
- **进度汇报**：长任务中途汇报进度，不待催促
- **交叉验证**：对关键数据主动寻找多来源比对
- **求助机制**：不确定时主动 @ 相关专家，不强行回答
- **沉默原则**：如问题已被完美回答，保持沉默避免冗余
